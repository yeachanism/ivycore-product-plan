이 문서는 랜딩페이지의 약속을 실제 학습 서비스의 기능·사용 흐름·권한·출시 조건으로 전환한다. 기능 우선순위와 운영 방식은 제안이며, 가격·제공 과목·강사진·정책이 확정된 것으로 취급하지 않는다.

만들 제품과 성공 기준

Ivycore는 IB 학생의 답안에서 학습 문제를 진단하고, 개인별 계획을 담당 선생님의 수업·과제·피드백·재점검으로 실행하는 학습 서비스다.

제품의 중심 단위는 학생 한 명의 과목별 학습 공간이다. 학생·학부모·선생님·어드민은 같은 학습 기록을 각자의 역할과 권한에 맞게 이용한다. 학생이 여러 과목을 수강하면 과목별 목표·계획·담당 선생님을 구분한다.

첫 버전의 성공 기준은 아래 흐름을 실제 계정으로 끝까지 운영할 수 있는 것이다.

상담 접수 → 진단 근거 확보 → 선생님의 진단 → 개인별 계획 → 튜터 배정·수강 합의 → 수업·과제 → 피드백·재제출 → 새로운 과제에서 재점검 → 학부모 보고·다음 계획

  • 학생은 다음에 무엇을 왜 해야 하는지 알고, 제출한 답안과 피드백을 다시 볼 수 있다.
  • 학부모는 어떤 어려움을 다루고 있는지, 무엇이 확인됐고 무엇이 아직 확인되지 않았는지 이해한다.
  • 선생님은 진단 근거와 이전 답안을 보고 수업을 준비하며, 다음 학습 판단을 기록한다.
  • 어드민은 각 학생의 담당자·현재 단계·다음 조치·지연 이유를 확인하고 처리한다.

랜딩에서 확인한 약속과 현재 상태

확인한 자료

  • 공개 랜딩, 프로그램 안내, 로드맵 예시, 피드백 예시.
  • 로컬 랜딩 소스 (내부 검토 자료), 프로그램 본문 (내부 검토 자료), 학습 예시 데이터 (내부 검토 자료), 상담 폼 (내부 검토 자료).
  • 현재 구현 설명 (내부 검토 자료), 운영 결정 대기 항목 (내부 검토 자료), 상담 운영 구조 기록 (내부 검토 자료).

공개 페이지에서 확인한 메인 문구는 ‘같은 목표, 다른 커리큘럼’이며, 현재 로컬 소스는 ‘IB에서 점수가 오르지 않는 이유부터 찾습니다’다. 두 버전에서 공통으로 확인되는 진단·학습 경로·튜터 매칭·피드백·재점검을 기획의 기준으로 삼았다. 이 문서는 소스와 공개 설명을 검토한 결과이며, 실제 수강 서비스나 운영 API의 새 검증 기록은 아니다.

필요한 연습을 지도할 튜터 연결 지도 가능 역량·시간·언어·정원을 확인한 배정 튜터 프로필은 예시
초안·첨삭·수정본·새 과제 연결 답안 버전, 위치를 지정한 피드백, 재제출, 적용 과제 예시 페이지의 학습 기록
My Plan·Progress·Messages 실제 학습 공간, 진척 기록, 과목별 대화 공개 학습 예시로 연결되는 링크
‘우리 아이’의 필요한 공부를 확인하는 CTA 자녀 연결, 보호자용 학습 보고와 일정·수강 관리 실제 학부모 계정·대시보드 없음
상담 접수 및 다음 단계 안내 접수함, 담당자 배정, 상담 진행·수강 전환 관리 저장·비공개 첨부·메일의 과거 운영 검증 기록 있음

랜딩의 목표 점수·튜터 인물·학습 사례를 실제 성과나 확보된 강사진의 근거로 사용하지 않는다. 상담 접수와 수강 계약·결제는 별개다.

초안의 가정

  1. 첫 형태는 반응형 웹이다. 학생·학부모는 모바일에서도 확인·제출하고, 선생님·어드민은 데스크톱에서 검토·운영한다.
  2. 기본 운영 모델은 1:1 수업 + 과제·첨삭이다. 수업 방식은 아직 확정되지 않은 가정이다. 수업 방식이 바뀌면 일정·과제 배정 구조를 조정한다.
  3. 진단·계획·피드백의 책임자는 선생님이다. 첫 버전의 매칭은 어드민이 근거를 확인해 배정한다.
  4. 첫 제공 과목은 실제 지도 인력과 자료가 준비된 IB 과목 1~2개를 권장한다. 랜딩의 과목 목록 전체가 수업 제공 범위라는 뜻은 아니다.
  5. 학생은 학습 주체, 학부모는 지원·수강 의사결정에 참여하는 역할로 설계한다. 학부모가 항상 결제자라는 가정은 두지 않는다.
  6. 첫 수업은 기존 화상 도구나 대면 방식으로 진행하고, 제품에는 일정·참여 링크·수업 기록을 남긴다. 실제 수업 도구는 운영자가 정한다.
  7. 계획 기간은 학생의 목표·학습량에 맞춰 입력한다. 첫 파일럿의 4–8주 계획은 제안이며 고정 수업 상품이나 성과 보장 기간이 아니다.

네 역할이 연결되는 전체 흐름

  1. 1
    상담 접수

    학생·학부모가 목표와 현재 어려움을 전달합니다.

  2. 2
    초기 진단

    어드민이 담당자를 정하고, 선생님이 답안이나 초기 과제를 검토합니다.

  3. 3
    맞춤 계획

    학습 목표와 과제, 다음 단계로 넘어갈 판단 기준을 정합니다.

  4. 4
    튜터 매칭·수강

    지도 범위와 가능한 시간을 확인하고 수강 조건에 합의합니다.

  5. 5
    수업·과제

    학생은 수업에 참여하고 과목별 과제를 제출합니다.

  6. 6
    피드백·재제출

    선생님의 피드백을 읽고, 수정 이유와 함께 새 답안을 제출합니다.

  7. 7
    새 문제에서 재점검

    다른 문제에서도 혼자 적용할 수 있는지 확인합니다.

  8. 8
    보고·다음 계획

    학생과 학부모에게 확인한 변화와 다음 학습을 안내합니다.

재점검 결과에 따라 다음 학습과 과제를 조정하고, 학습 주기를 이어갑니다.

핵심 기능의 상세 규칙

9.1 진단: 관찰과 근거를 먼저 저장

진단 한 건에는 다음 내용이 필요하다.

  • 학생·과목·세부 트랙·HL/SL·평가 유형·평가 기준 버전.
  • 사용한 답안/초기 과제, 작성 날짜, 수행 조건, 도움을 받은 여부.
  • 잘 수행한 부분과 보완할 부분, 근거가 되는 문장·페이지·문항.
  • 우선 학습 목표 1~3개, 그 목표를 먼저 다루는 이유, 다음 연습.
  • 다음에 확인할 과제와 판단 기준, 작성·검토 선생님, 발행 시점.
  • 근거 충분 여부와 추가 확인 요청. 기존 성적은 평가 종류·시점을 함께 표시.

자료 없이 신청해도 접수할 수 있다. 이 경우 담당 선생님이 초기 과제나 확인 활동을 지정하고, 근거가 확보될 때까지 진단을 확정하지 않는다. 레이더 차트는 기준과 데이터가 준비된 경우에만 제공하며, 자료가 없을 때 임의 점수를 채우지 않는다.

과목의 채점 기준과 학습 관찰 항목을 구분한다. 예를 들어 문항별 마크스킴을 사용하는 수학에 공통 고정 배점을 붙이거나, 서로 다른 평가 유형의 점수를 직접 비교하지 않는다. 최신 기준의 검토·승인은 운영자가 출시 전에 수행해야 한다.

9.2 로드맵: 약점에서 과제와 판단으로 연결

로드맵 단계에는 관련 진단 → 학생의 할 일 → 제출물 → 선생님의 검토 항목 → 단계 이동 기준 → 재점검 시점을 둔다.

랜딩의 개념 확인·답안 구성·문제 적용·재확인 흐름을 기본 템플릿으로 삼는다. 모든 학생이 같은 순서를 같은 기간 동안 수행하도록 고정하지 않는다. 과목과 진단에 맞게 단계·과제·기간을 조정한다.

단계 이동은 선생님의 판단과 근거 답안으로 기록한다. 과제 제출이나 수업 출석만으로 해당 역량을 달성 처리하지 않는다. 계획을 변경할 때는 변경 전·후, 이유, 적용일을 보존하고 학생·학부모에게 알린다.

9.3 과제·피드백: 원본과 수정본을 연결

과제에는 학습 목표, 설명·자료, 제출 방식, 마감, 확인 기준을 둔다. 답안 제출은 버전을 만들고, 피드백은 해당 버전에 연결한다. 수정본이 올라와도 이전 답안과 피드백을 덮어쓰지 않는다.

피드백의 최소 구성은 어느 부분 → 무엇이 확인됐는지 → 왜 보완이 필요한지 → 학생이 다음에 할 일이다. 재제출과 함께 수정 이유를 남기고, 이후 새 문제에 적용하는 과제를 별도 배정한다.

9.4 진척·보고: 참여와 학습 확인을 구분

진척 화면에는 아래 세 가지를 분리해 보여준다.

  1. 참여: 수업 출결, 과제 제출·지연, 피드백 확인.
  2. 학습 근거: 초안→수정본에서 확인한 변화, 새 문제에서 혼자 수행한 여부, 아직 확인되지 않은 항목.
  3. 평가 결과: 학교 시험·모의 평가 등의 실제 기록과 평가 시점·출처. 목표 점수와 별도 표시.

학부모 보고는 기간·학습 목표·수행 내역·개선 근거·남은 어려움·다음 계획·지원 요청을 포함한다. 초기 제안은 주간 요약과 계획 구간 종료 보고이며, 실제 주기는 수업 상품에 맞춰 정한다.

예시 보고 문장: “초안에서 빠졌던 근거와 해석의 연결을 수정본에 추가했습니다. 새로운 지문에서 혼자 같은 연결을 만드는지는 다음 과제에서 확인합니다.” 이 문장은 보고 형식 예시이며 실제 학생 성과가 아니다.

9.5 수업·수강·운영

  • 일정에는 선생님·학생·과목·시작/종료·시간대·진행 방식·참여 정보를 둔다. 확정 시 양쪽의 시간 중복을 확인한다.
  • 변경·취소는 요청→운영 확인→결과 통보 흐름으로 처리하고 기존 일정과 변경 이력을 보존한다.
  • 수강 제안에는 과목·튜터·기간·횟수·수업 및 첨삭 범위·비용·변경 조건을 명시한다. 상담 접수만으로 수강을 시작하지 않는다.
  • 첫 버전의 입금 확인·환불·튜터 정산은 담당자가 근거와 처리 상태를 기록한다. 실제 확인 전에는 완료로 표시하지 않는다.
  • 수업 중 사용한 자료와 다음 과제를 수업 기록에 연결한다. 지각·결석·취소의 수업 차감 기준은 출시 전에 정한다.

  • 보호자는 여러 자녀, 학생은 정책에 따라 여러 보호자와 연결할 수 있다. 관계 해제 시 접근을 회수한다.
  • 선생님은 배정된 과목 공간을 기준으로 접근한다. 재배정·종료·계정 정지 시 조회·다운로드 권한도 다시 확인한다.
  • 비공개 첨부는 서버가 역할·관계를 확인한 뒤 제한된 시간 동안 접근시킨다. 메뉴를 숨기는 것만으로 접근을 막지 않는다.
  • 알림 이메일에는 민감한 답안·성적·대화 원문을 넣지 않고 로그인 후 확인할 링크를 제공한다.

상태 변경의 권한과 책임자를 상세 설계에서 각 동작에 연결한다. 처리 기한이 지난 업무는 자동 완료하지 않고 담당자의 지연 업무로 보인다.

개발을 시작할 때의 순서

  1. 공통 기반: 계정·역할·자녀 연결·과목별 학습 공간·비공개 파일 권한. 네 역할로 같은 테스트 학생을 조회하고 타 학생 접근이 차단되는지 확인.
  2. 상담→계획: 어드민 접수/배정, 학생 자료/초기 과제, 선생님 진단·계획 발행, 학생·보호자 열람.
  3. 매칭→학습: 튜터 수락·수강 조건·일정·과제 제출·피드백·재제출·새 과제 확인.
  4. 보고→운영: 학부모 보고·대화·알림·지연/예외·수강/정산 기록·인수인계.
  5. 실제 파일럿: 확정된 과목·선생님·정책으로 실제 학생의 한 학습 주기를 운영하고 병목을 기록.

각 단계는 앞 단계의 데이터와 권한을 재사용한다. 개발 기간·예산은 운영 조건과 화면 상세를 확정한 뒤 산정한다.
